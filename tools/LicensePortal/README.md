# Company-side License Portal — development only

This separate ASP.NET Core project stores customer, subscription and issuance/revocation approval jobs in PostgreSQL. It accepts no signing private key and must never ship to customers. The issuer remains a separate authority; approved job export is a handoff, not automatic issuance. The export itself is not a cryptographically authenticated approval token; an authorized issuer operator must verify the record and use the authoritative issuance ledger. Do not claim end-to-end dual-controlled signing until that boundary is enforced.

Provision a PostgreSQL database and apply schema.sql as a migration identity. Configure a separate least-privileged application database role (SELECT, INSERT, and UPDATE only on job decision columns, plus audit sequence usage; no DELETE or audit modification). Set ConnectionStrings__Licensing through protected configuration, Portal__Origin to the exact HTTPS authority, Portal__OperatorPins to a private JSON file mapping uppercase SHA-256 leaf certificate fingerprints to {"id":"operator-id","role":"requester"|"reviewer"}. Use independently issued software client certificates with client-auth EKU and independent server TLS. Set ASPNETCORE_URLS to the HTTPS listener and configure its certificate using protected ASP.NET configuration. No forwarded identity or plain HTTP is accepted. Remove/replace revoked operator pins and restart through approved operations. Pin validation is not MFA; production MFA, credential rotation, enforced signing approval, business billing and resilient database acceptance are outstanding.

UI supports customer/subscription creation, signed request validation, immutable pending requests, atomic approval/rejection by a distinct reviewer, audit in the same transaction and approved package export. Customer systems need no connection to this portal. Use only disposable identities and keys in CI. The existing CLI issuer remains local and independent. No external service or real key provisioned by this PR.

## Approved database signing worker
The company-side LicenseIssuerWorker is a separate executable, loading an encrypted software PKCS#8 signing key only in its own process. The worker reads an independently approved immutable job directly from PostgreSQL, not from exported JSON; locks the subscription row, rejects stale terms, validates proof of possession, enforces node/site limits and globally unique installation binding, and commits allocations and exact signed response in the same DB transaction. Repeated execution returns the committed result. Revocation permanently reserves the old seat; approved terms renewal increments the subscription revision. The portal can retrieve completed output without signing authority. Configure GATEWAYCORE_ISSUER_DB with a separate restricted worker identity. Never grant the worker UPDATE on approval columns or grant the web portal writes to issuer tables. The legacy local CLI is a development-only alternate authority and must not be provisioned against the same commercial subscriptions. Real PostgreSQL concurrent approval/issuance integration tests and deployment role grants still pending; exported approved JSON is informational, not signing authorization.

## Database privilege separation
Provision distinct non-owner LOGIN roles `gc_portal_requester`, `gc_portal_reviewer` and `gc_issuer_runtime` with no inherited write privileges. Apply schema.sql and then runtime-grants.sql as migration owner; restrict schema CREATE to migration administrators. Configure ConnectionStrings__Licensing for requester/read operations, ConnectionStrings__LicensingReviewer for decisions, and GATEWAYCORE_ISSUER_DB for the separate worker. Never use a superuser or shared credential. The database now denies requester approval, worker approval and portal signing-table writes; the decision trigger rejects subsequent modifications. This does not isolate two credentials inside a compromised portal process or guarantee independently authenticated human identities; production MFA and external audit remain necessary. Runtime roles cannot update or delete audit rows; a database owner still can.

## Multifactor operator authentication
Each pinned client certificate must also have an independent strong operator password. Generate a unique ASP.NET Identity V3 hash interactively using `dotnet run --project tools/LicensePortal -- --hash-password`; place only the hash in a private JSON mapping operator ID to hash, configured through Portal__PasswordHashes. Keep the password independent of the certificate private key and store the hash configuration outside Git. Certificates and passwords alone cannot access licensing APIs. Sessions are certificate-identity-bound, 15-minute absolute lifetime, one active session per identity, Secure/HttpOnly/SameSite=Strict cookies, and process-local five-failure/five-minute throttling. A portal restart invalidates sessions; distributed MFA sessions and throttling are not implemented. The portal process still has both DB credentials; stronger process separation and operational audit remain pending.
